## Native authority and transport

The `ArdiaDocuments.call` adapter allows only watch, commit, flush and unwatch. The existing engine transport dispatches these before the ordinary engine-service allowlist. Requests retain the existing profile-string restriction, bounded JSON text and structured rejection path. Document requests also require exactly the three transport keys and a JSON depth of at most 48. Watch/unwatch require exactly `{document:'live.json'}` before subscription state changes; the helper validates commit/flush shapes and operation bounds. The helper result dictionary is serialized exactly once by `Resolve`, with optional conflict details such as `reason:'notOwner'` untouched. Helper error code/message propagate unchanged; the host adds no operation echo or secret-bearing diagnostic.

`DocumentsFor` runs on UI, checks the actual regular native Profile and its nonempty native path, and keys a weak registry by that actual profile's document directory. There is no requested-path or unsupported-profile fallback. A shared `DocumentAuthority` gives sibling browser/utility hosts one opaque native scope and one `SequenceBound<LinuxDocumentService>` on the existing sequenced BLOCK_SHUTDOWN FileRunner. The service and its canonical helper are constructed, called and destroyed there. Read/write callbacks capture immutable copied paths, never native Profile pointers. Weak renderer reply callbacks do not own accepted service work. Destroying the last UI authority queues worker destruction after already accepted operations; peer hosts retain their shared authority.

Client IDs combine the native authority scope, a native per-window UUID and the activated native renderer generation. `EnsureDocumentClient` caches that trusted identity only after the actual handler passes committed-document authorization, Javascript allowance and regular-profile checks. An inactive retirement generation cannot mint a client. Cleanup copies the previously authenticated client rather than rebuilding authorization from a counter or accessing a retired Profile. Retirement clears the cached identity before advancing generation. Document calls and close requests require current authorization; close acknowledgment checks it before enqueueing Seal as well as after the worker reply. Requests cannot supply client identity, authority or paths.

Changes are posted to UI and filtered by current native scope, regular profile, subscription token, renderer generation and the existing authorized event sender. Unwatch/re-watch advances the subscription token. Source events are delivered as well as peer events. Retirement posts matching close-seal cancellation and unwatch for only the retiring client. Accepted worker persistence and peer fanout continue when the source renderer disappears.

`ReadCanonicalDocument` distinguishes file-not-found, present-invalid JSON and read/access errors. Canonical corruption fails in the helper rather than importing legacy data. Internal callbacks use the bounded native reader and atomic native writer directly. Both Live filenames are rejected in generic read/write/save/remove and skipped during bootstrap enumeration, while those internal import/envelope callbacks remain usable.

## Close barrier

Every hosted widget installs the existing `MakeCloseSynchronous` interception, including regular browser windows. Requests emit the agreed ArdiaShell/shell envelope with opaque decimal renderer and close generations. Repeated requests share the pending identity. `requestWindowClose` can request a same-profile target's renderer barrier; acknowledgment and rejection act only on the calling native host and exact current identity. Bare `closeWindow` requests the barrier and has no unconditional close path.

Acknowledgment starts a native sealing phase. Later watch/commit, session writes and generic document mutations are blocked. Previously accepted file work precedes Seal on FileRunner. Session/generic write outcomes are tracked per native renderer; unresolved writes or failures block final close, and only successful retry of the same storage name clears its failure. The helper Seal must succeed with the exact own-client durable watermark. A window that never attempted watch may skip Live Seal only for watermark zero; the native write gate prevents it from opening a document subscription during that attempt.

After worker success, UI rechecks the native pending identity, active authorized renderer, regular profile and live widget. It marks the attempt sealed and requests the ordinary BrowserWindow close. The widget interception checks ownership again before allowing Chromium's normal close handling. It does not set force-skip flags or bypass page beforeunload. Acknowledgment replies await WidgetClosing after the durability gate, rather than treating the request as completed closure. Browser detachment or renderer loss can reject/drop surviving replies; accepted worker work remains independent of those replies.

The 30-second native deadline cancels instead of force-closing. Cancellation is confirmed only after matching CancelSeal returns on FileRunner. A pending acknowledgment then rejects, allowing the existing JS barrier to request confirmed cancellation before resuming its token-scoped producers. Failed seal/storage operations retain the window; stale acknowledgments/rejections and renderer replacements cannot approve a newer attempt. Repeated acknowledgments share one worker seal and must use the same watermark. Lost replies can repeat that identity; worker or storage failure results are retained for immediate same-generation replay until cancellation. Renderer retirement cancels its outstanding seal before removing its subscription.

The only insertion needed in bridge-owned renderer lifecycle logic is `if (!RetireDocuments()) return;` at the beginning of `ShellHostView::RetireRenderer()`, before generation advancement. The separately implemented helper owns all F04 cleanup, copies its native client and authority, and returns a weak survival check after delivering retired replies. The bridge renderer fixture adds only a declaration-compatible stub for that call. DetachBrowser also checks the cleanup survival result before accessing the host again; the destructor invalidates UI weak pointers before cleanup. Preserve this insertion when applying the bridge correction; do not merge an older replacement of RegisterMessages or temporary disposal from this branch.

## Close routes and materialization limits

Read-only inspection used the retained Chromium 155 source at `/home/mac/ardia-linux-build/chromium_git/chromium/src`. The following classification describes those source call chains and explicitly identifies inference; it is not Chromium 156 API qualification or runtime evidence.

| Path | Ordinary or exceptional reachability | What the current gate establishes |
| --- | --- | --- |
| `DesktopWindowTreeHostPlatform::OnCloseRequest` to `GetWidget()->Close`; window controls/keyboard/renderer close to `BrowserView::Close` to widget Close | Ordinary close. The compositor request path itself is visible in the retained source. | `Widget::CloseWithReason` consumes the installed override before widget closure or BrowserView close handling. An authorized Seal and fresh UI ownership check are required before this entry continues. The fixture reasons are simulated, not physical input evidence. |
| `BrowserCloseManager::CloseBrowsers` to BrowserWindow Close with `ShouldIgnoreUnloadHandlers()==false` | Ordinary application quit after beforeunload/download checks. | This particular BrowserWindow Close invocation reaches the widget gate. It does not prove every earlier unload-preflight path reaches that invocation. Global quit cancellation and beforeunload reentrancy remain unqualified. |
| `UnloadController::OnWindowCloseComplete` posting `BrowserManagerService::SynchronouslyDestroyBrowser` | Also part of ordinary close completion, not solely a forced shutdown API. `OnWindowClosing` calls it when tabs are empty. `ProcessPendingTabs` can call OnWindowClosing directly. | It inherits a seal only if its causal close attempt already passed the widget gate. There is no explicit seal check at this destruction scheduling point. Ordinary quit preflight sets `is_attempting_to_close_browser_`; if a beforeunload tab is detached/crashes and both pending sets become empty, the posted ProcessPendingTabs rescan can reach OnWindowClosing without waiting for a deferred widget close. That source-level interleaving is an uncovered ordinary-quit route; it has not been reproduced in Chromium 156. |
| `BrowserWidget::OnNativeWidgetDestroyed` to force-skip warnings, OnWindowClosing and SynchronouslyDestroyBrowser | Runs during normal terminal native-widget teardown, and can also follow unexpected platform-window loss. It is not inherently an exceptional force-quit request. | Normal teardown following the approved widget gate inherits its seal. Unexpected destruction without that entry has no JS drain guarantee. The notification occurs after native-widget destruction and cannot itself veto the loss. |
| BrowserCloseManager's `ShouldIgnoreUnloadHandlers` branch, then CloseAllTabs and SynchronouslyDestroyBrowser | Explicit exceptional end-session or silent-exit policy: the retained predicate tests `kEndSession` or `kSilentExit`. | Even if BrowserWindow Close is deferred, the following destructive calls bypass the widget veto. Pending renderer-only intent is not guaranteed. |
| Direct `views::Widget::CloseNow` or browser ownership release | CloseNow ignores the override. BrowserWidget's destructor normally uses it for owned child widgets during teardown; direct calls on a hosted root or an independently hosted child would bypass that host's seal. `BrowserManagerService::Shutdown` also releases remaining browser ownership directly during service shutdown, without requiring the force-quit predicate. | A previously sealed host retains that prior guarantee; an unsealed hosted root/child or remaining service-owned browser has no renderer-drain guarantee. The retained ordinary root Close path does not call root Widget::CloseNow as its initial request. Independently hosted child ownership needs version-correct qualification. |
| `DesktopWindowTreeHostPlatform::CloseNow` downstream of native Close | This backend method also occurs during normal platform teardown after approved Widget Close; it is distinct from a direct call to `views::Widget::CloseNow`. | Its name alone does not establish a bypass. Unsolicited platform OnClosed/native destruction still cannot be vetoed after the fact. |
| Browser crash, abort, OS termination or power loss | Exceptional process/storage loss. | Neither JS timer draining nor completion of queued worker tasks is guaranteed. Atomic replacement is not power-loss qualification. |

For any UI-destruction path while the browser process and FileRunner continue normally, already queued native work is owned independently of renderer replies, uses copied immutable paths/clients and precedes service destruction on the same sequence. Thus accepted jobs still execute and successful writes can persist even if replies or UI events are lost; validation/storage failures remain failures. During orderly ThreadPool shutdown, already accepted BLOCK_SHUTDOWN tasks are waited for. This does not turn queued work into an acknowledged successful commit, recover JS-only timers, guarantee peer delivery to destroyed scopes or establish crash/power-loss durability. Process termination can interrupt even accepted work.

The version-correct Linux patch still required for full ordinary-close coverage is a native close-authority predicate/request hook at the start of `UnloadController::OnWindowClosing`, before tab closure or OnWindowCloseComplete, plus a seal recheck before `OnWindowCloseComplete` sets `is_delete_scheduled_` and emits browser-did-close. For an Ardia-owned browser, an unsealed live scope must request its existing generation-bound barrier and defer destructive work; only successful worker Seal plus fresh UI authorization may resume the normal Chromium path. Beforeunload and warning decisions stay in Chromium/shared policy. This closes the direct ProcessPendingTabs path rather than trying to veto a post-close observer.

Forced end-session/silent-exit handling additionally needs a distinct guard in `BrowserCloseManager::CloseBrowsers` before CloseAllTabs/SynchronouslyDestroyBrowser. Direct hosted-root CloseNow/destruction must be routed through that authority before native teardown begins. A guard only inside SynchronouslyDestroyBrowser is insufficient: some callers assume immediate destruction, native-widget destruction is already irreversible, and service Shutdown releases browser ownership without that function. Remaining-browser shutdown must therefore be coordinated before `BrowserManagerService::Shutdown` starts releasing entries; blocking its UI teardown on callbacks that require UI would be unsafe. An OS-imposed termination deadline needs an explicit narrower policy instead of claiming it preserved JS-only intent. These are precise required patch locations/contracts, not implemented or verified Chromium 156 hooks.

Shared Ardia warnings/confirmation remain F21/F05 work. No warning choices or force-skip behavior are introduced by F04. Full ordinary quit coverage, forced-shutdown policy and independently hosted child teardown remain open alongside matching-engine runtime validation.

No new Chromium patch is added. The existing Linux layer materialization copies `engine/ardiacore-linux/src/ardia/linux`, including the new service/close files. The existing Linux-only GN target now includes the canonical helper sources and headers and the host glue. The minimal launch target, shared engine choices and macOS sources are unchanged.
